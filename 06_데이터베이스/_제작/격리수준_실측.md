# 격리수준·잠금 실측 결과 (07단원 재료)

**환경**: PostgreSQL 18.6 (docker postgres:18-alpine, 127.0.0.1:5434, factory/secret/factory_db)
전부 실제로 두 개의 연결을 띄워서 재현한 것입니다. PGlite 로는 못 합니다(연결이 하나뿐).

## 재현 결과

| 시험 | READ COMMITTED (기본) | REPEATABLE READ |
| --- | --- | --- |
| 반복 불가 읽기 — 같은 SELECT 를 두 번 | 100 → **999 로 달라짐** | 100 → 100 (같음) |
| 팬텀 읽기 — 같은 COUNT 를 두 번 | 2건 → **3건으로 늘어남** | 2건 → 2건 (안 생김) |

```
SERIALIZABLE : B 커밋이 거절됨
   40001  could not serialize access due to read/write dependencies among transactions

데드락 : 한쪽만 죽음
   40P01  deadlock detected
```

## ★★★ 교과서와 다른 점 — 반드시 자료에 넣으세요

SQL 표준은 이렇게 정합니다.

```
              더티읽기   반복불가읽기   팬텀읽기
READ UNCOMMITTED   허용      허용        허용
READ COMMITTED     막음      허용        허용
REPEATABLE READ    막음      막음        ★ 허용
SERIALIZABLE       막음      막음        막음
```

**그런데 PostgreSQL 의 REPEATABLE READ 는 팬텀도 막습니다.** 위에서 실제로 확인했습니다.

이유: Postgres 는 잠금이 아니라 **스냅샷 격리(MVCC)** 로 구현했습니다.
트랜잭션이 시작한 순간의 사진을 계속 보기 때문에, 남이 새 줄을 넣어도 그 사진에는 없습니다.

★ 그리고 Postgres 에는 `READ UNCOMMITTED` 가 사실상 없습니다.
써도 `READ COMMITTED` 로 동작합니다. 더티 읽기는 아예 안 일어납니다.

★ 학생이 "표에는 팬텀이 허용이라던데요?" 라고 물을 것입니다.
**표는 표준이고, 실제 구현은 더 강할 수 있습니다.** 이걸 가르치세요.

## 재현하는 법 (코드 뼈대)

```js
import pg from "pg";

const 새연결 = async () => {
  const 연결 = new pg.Client({
    host: "127.0.0.1", port: 5434,
    user: "factory", password: "secret", database: "factory_db",
  });
  await 연결.connect();
  return 연결;
};

const 가 = await 새연결();
const 나 = await 새연결();

await 가.query("BEGIN ISOLATION LEVEL READ COMMITTED");
const 첫번째 = (await 가.query("SELECT 값 FROM 잔고 WHERE id=1")).rows[0].값;

await 나.query("UPDATE 잔고 SET 값=999 WHERE id=1");   // 다른 연결이 끼어듭니다

const 두번째 = (await 가.query("SELECT 값 FROM 잔고 WHERE id=1")).rows[0].값;
await 가.query("COMMIT");
// 첫번째 !== 두번째  ← 반복 불가 읽기
```

데드락은 두 UPDATE 를 `await` 없이 띄워 놓고 `Promise.allSettled` 로 받으세요.
한쪽만 `40P01` 로 죽습니다.

## ★ 단원끼리 안 부딪히게

07~10단원이 같은 데이터베이스를 씁니다. 각 단원은 **자기 스키마**를 쓰세요.

```js
await 연결.query("CREATE SCHEMA IF NOT EXISTS 단원07");
await 연결.query("SET search_path TO 단원07");
```

각 파일 맨 앞에서 자기 표를 `DROP TABLE IF EXISTS` 하고 새로 만드세요.
그래야 여러 번 돌려도 같은 결과가 나옵니다.

## 아직 안 잰 것

- 잠금 종류별 충돌 (`SELECT FOR UPDATE` / `FOR SHARE` / `NOWAIT` / `SKIP LOCKED`)
- 낙관적 잠금 (버전 칸) vs 비관적 잠금 — 같은 시나리오로 비교
- `pg_locks` 로 지금 무엇이 잠겨 있나 보기
- 긴 트랜잭션이 VACUUM 을 막는 것
- MySQL 의 REPEATABLE READ 는 팬텀을 어떻게 처리하나 (갭 락) — 09단원과 겹칩니다
