# 개념 01 — 왜 옮기나

여기서부터 진행 방식이 바뀝니다.

- **01~07단원**: `.html` 파일을 더블클릭 → 브라우저가 열림
- **08단원부터**: 터미널에 `npm run dev` → 브라우저가 열림

바뀌는 게 이것 하나뿐인데도, 이 자료에서 학생이 가장 많이 멈추는 곳이 여기입니다.
그래서 **왜 바꾸는지부터** 확실히 하고 넘어갑니다.
납득이 안 된 채로 설치를 시작하면, 에러가 한 번 났을 때 그만두게 됩니다.

## 이 문서는 읽기만 하는 문서입니다

여기서는 아무것도 설치하지 않습니다. 터미널도 안 엽니다.
**손을 움직이는 것은 개념02부터입니다.** 이 문서는 10분쯤 읽고 넘어가면 됩니다.

먼저 결론을 말해 두겠습니다.

> Vite 는 "React 를 제대로 쓰려면 반드시 있어야 하는 것" 이 아닙니다.
> 지금 방식이 **불편해져서** 바꾸는 것입니다.
> 그 불편함을 여러분은 이미 07단원까지 오면서 직접 겪었습니다.

아래에서 그 불편함 네 가지를 하나씩 봅니다.
전부 여러분이 실제로 겪은 것들입니다.

## 한계 1 — 파일을 못 나눈다

### 지금 무슨 일이 벌어지고 있나

여러분이 지금까지 읽은 `.html` 파일을 세어 보면 이렇습니다.

| | |
|---|---|
| 01~07단원 `.html` 파일 수 | **49개** |
| 전부 합친 줄 수 | **27,880줄** |
| 파일 하나 평균 | 약 570줄 |
| 가장 긴 파일 | 733줄 (`05_조건부_렌더링과_리스트/개념03_key.html`) |

한 파일이 500~700줄입니다. 스크롤을 위아래로 한참 굴려야 끝까지 갑니다.

07단원 `개념01_불변하게_바꾸기_배열.html` 은 **715줄 안에 컴포넌트가 6개** 들어 있습니다.
세 번째 컴포넌트를 고치려고 내려갔다가, 첫 번째 컴포넌트를 다시 보려고 올라오고,
다시 내려가고 — 이 왕복을 여러분은 계속했습니다.

더 심한 게 하나 있습니다.
파일 위쪽의 `<style>` 블록(85줄)은 **49개 파일에 전부 똑같이 복사돼 있습니다.**
버튼 색을 파란색에서 초록색으로 바꾸고 싶다면 **49군데를 고쳐야 합니다.**
한 군데를 빠뜨리면 그 파일만 파란 버튼으로 남습니다.

03단원 개념05에서 "쪼개면 고칠 곳이 한 곳이 된다" 고 배웠습니다.
그런데 정작 이 자료 자신이 그 반대로 되어 있었던 것입니다.

### 왜 못 나눴나

01단원 개념02에서 이 뼈대를 썼습니다.

```html
<script type="text/babel">
  function MenuRow({ name, price }) { ... }
</script>
```

이렇게 만든 `MenuRow` 는 **그 파일 안에서만 삽니다.**
다른 `.html` 파일에서 `MenuRow` 를 부를 방법이 없습니다.

그래서 03단원에서 만든 `MenuRow` 를 05단원에서 또 쓰려면
**복사해서 붙여 넣는 수밖에 없었습니다.**
그리고 붙여 넣은 순간 그것은 다른 물건이 됩니다. 한쪽만 고쳐지고 두 벌이 어긋납니다.

`<script>` 태그를 여러 개 넣어서 파일을 나누는 방법이 아예 없지는 않습니다.
다만 그렇게 하면 만든 이름이 전부 페이지 전체에 그대로 노출됩니다.
`Card` 라는 이름을 두 파일에서 쓰면 나중에 읽힌 쪽이 앞의 것을 조용히 덮어씁니다.
에러도 안 납니다. 화면만 이상해집니다.

### Vite 를 쓰면

파일을 나누고, 필요한 곳에서 **가져다 씁니다.**

```jsx
// _부품/MenuRow.jsx  ← 이 파일에만 있습니다
export default function MenuRow({ name, price }) { ... }
```

```jsx
// 쓰는 쪽 파일
import MenuRow from "./_부품/MenuRow.jsx";
```

`import` 와 `export` 라는 문법인데, **개념03에서 처음부터 배웁니다.**
지금은 "파일을 나눌 수 있게 된다" 만 알면 됩니다.

이렇게 하면 `MenuRow` 는 세상에 **하나만** 존재합니다.
고칠 곳이 한 곳이 됩니다. 03단원에서 컴포넌트로 쪼갤 때 얻었던 이득과 똑같은 이득입니다.
이번에는 그것을 파일 단위로 하는 것입니다.

## 한계 2 — 브라우저가 열 때마다 Babel 로 번역한다

### 지금 무슨 일이 벌어지고 있나

01단원 개념02에서 파일 위쪽 script 3줄을 설명했습니다. 그중 세 번째가 이것이었습니다.

```html
<script src="../_lib/babel.min.js"></script>
```

Babel 이 하는 일은 하나입니다. **JSX 를 브라우저가 아는 자바스크립트로 번역하는 것.**
브라우저는 `<h3>안녕</h3>` 같은 문법을 모르기 때문에 누군가 번역해 줘야 합니다.

문제는 **그 번역이 어디서 일어나는가**입니다.
지금은 **여러분의 브라우저 안에서, 파일을 열 때마다** 일어납니다.

`_lib` 폴더 안의 파일 크기를 재 보면 이렇습니다.

| 파일 | 크기 | 하는 일 |
|---|---|---|
| `babel.min.js` | **2,977 KB** | JSX 번역기 |
| `react-dom.development.js` | 1,054 KB | 화면에 붙이기 |
| `react.development.js` | 107 KB | 화면 설명 만들기 |

합쳐서 약 **4 MB** 입니다.
그리고 그중 **2,977 KB(전체의 70%)가 번역기 하나**입니다.

F5 를 누를 때마다 브라우저는 이 4 MB 를 다시 읽고,
2,977 KB 짜리 번역기를 켜서, 여러분의 코드를 처음부터 다시 번역합니다.
`console.log` 한 줄만 고쳐도 전부 다시 합니다.

### 콘솔에 나오던 그 노란 경고

01단원 개념01에서 "정상이니 무시하세요" 라고 하고 넘어간 줄이 있습니다.

```
You are using the in-browser Babel transformer.
Be sure to precompile your scripts for production - https://babeljs.io/docs/setup/
```

우리말로 옮기면 이렇습니다.

> "지금 번역기를 **브라우저 안에서** 돌리고 계시네요.
>  실제로 남들에게 보여 줄 때는 **미리 번역해 두세요.**"

Babel 이 직접 "이건 연습용 방식이다" 라고 알려 주고 있었던 것입니다.
그 경고가 시키는 "미리 번역해 두기" 를 해 주는 도구가 **Vite** 입니다.

### Vite 를 쓰면

번역이 **여러분의 컴퓨터에서 미리** 끝납니다.
브라우저는 이미 번역이 끝난 코드만 받습니다.

- `babel.min.js` 를 실을 필요가 없습니다. 2,977 KB 가 통째로 사라집니다.
- 파일을 고치면 **고친 파일 하나만** 다시 번역합니다. 나머지는 그대로 둡니다.
- 그래서 저장하고 화면이 바뀌기까지 거의 기다림이 없습니다.

앞으로 콘솔에서 저 노란 Babel 경고는 다시 안 보게 됩니다.

## 한계 3 — 라이브러리를 못 가져다 쓴다

### 지금 무슨 일이 벌어지고 있나

지금 방식으로 React 를 쓰려면 이렇게 해야 했습니다.

1. `react.development.js` 와 `react-dom.development.js` 파일을 어디선가 구해 와서
2. `_lib` 폴더에 직접 넣고
3. `<script src="...">` 로 **순서를 맞춰** 싣는다

순서까지 맞춰야 했습니다. `react-dom` 은 `react` 를 쓰기 때문에 `react` 가 먼저 와야 합니다.
도구가 3개면 순서가 3개, 10개면 10개를 전부 여러분이 맞춰야 합니다.

그런데 더 큰 문제가 있습니다.
**그런 식으로 쓸 수 있는 파일을 아예 안 주는 도구가 많습니다.**

브라우저에 `<script src>` 로 바로 넣을 수 있게 만든 파일을 **UMD 빌드**라고 부릅니다.
요즘 도구들은 이걸 잘 안 만듭니다. 그리고 —

> **React 도 19 버전부터 UMD 빌드를 없앴습니다.**

즉 이 자료가 01~07단원에서 쓴 React 18.3.1 은, 그 방식이 가능한 **마지막 버전**입니다.
이 이야기는 뒤에서 한 번 더 나옵니다(개념02).

11단원에서 배울 `react-router-dom` 같은 것도 마찬가지입니다.
지금 방식으로는 시작조차 할 수 없습니다.

### Vite 를 쓰면

터미널에 한 줄이면 끝납니다.

```
npm install react-router-dom
```

- 파일을 어디서 구할지 고민할 필요가 없습니다.
- 그 도구가 다시 필요로 하는 다른 도구까지 **알아서 같이 받아 옵니다.**
- 순서도 알아서 맞춰집니다.

`npm` 이 무엇인지는 개념02에서 설명합니다.
지금은 "필요한 도구를 받아다 주는 심부름꾼" 정도로 봐 두세요.

여러분이 쓸 실습프로젝트에는 `react-router-dom` 이 **이미 받아져 있습니다.**
11단원에서 바로 쓰게 됩니다.

## 한계 4 — 고칠 때마다 F5 를 눌러야 한다

### 지금 무슨 일이 벌어지고 있나

01단원 개념02 섹션 4에서 이 절차를 배웠습니다.

```
코드를 고친다  →  Ctrl + S 로 저장  →  브라우저에서 F5
```

그리고 "안 바뀌면 이것부터 확인하세요" 라고 여러 번 적혀 있었습니다.
그만큼 자주 빠뜨리는 단계이기 때문입니다.

그런데 F5 에는 더 성가신 문제가 하나 더 있습니다.
**F5 를 누르면 화면이 처음 상태로 돌아갑니다.**

07단원에서 장바구니를 만들 때를 떠올려 보세요.

1. 아메리카노를 5번 담는다
2. 5개일 때 화면이 이상해서 글자 하나를 고친다
3. 저장하고 F5 를 누른다
4. **장바구니가 텅 빈 상태로 돌아온다**
5. 아메리카노를 다시 5번 담는다
6. 또 뭔가 이상해서 고친다 → F5 → 또 텅 빈다

state 는 브라우저 메모리 안에만 있습니다. 새로고침하면 사라집니다.
그래서 "여러 번 눌러야 나오는 화면" 을 고칠 때는 매번 처음부터 다시 만들어야 했습니다.

### Vite 를 쓰면

저장만 하면 화면이 **저절로** 바뀝니다. F5 를 안 누릅니다.

이걸 **HMR**(Hot Module Replacement, 뜨거운 모듈 교체)이라고 부릅니다.
이름이 거창한데 하는 일은 이렇습니다.

> 페이지를 통째로 새로 여는 게 아니라, **고친 파일만 살짝 갈아 끼웁니다.**
> 나머지는 돌아가던 그대로 둡니다. 그래서 **state 가 살아남습니다.**

위 장바구니 예로 다시 보면 이렇게 됩니다.

1. 아메리카노를 5번 담는다
2. 글자를 고치고 저장한다
3. **장바구니에 5개가 담긴 채로** 글자만 바뀐다

고쳤는지 확인하려고 같은 조작을 반복하는 일이 없어집니다.
09단원부터는 이 차이가 아주 크게 느껴질 것입니다.

## 그래서 Vite 가 뭔가요

Vite(비트)는 **개발을 도와주는 도구**입니다. 프랑스어로 "빠르다" 라는 뜻입니다.
하는 일은 크게 두 가지입니다.

**① 개발하는 동안 — 작은 웹 서버 역할**

`npm run dev` 를 하면 여러분 컴퓨터 안에 작은 서버가 하나 켜집니다.
브라우저는 파일을 직접 여는 게 아니라 이 서버에게 받아 갑니다.
그 사이에서 Vite 가 JSX 를 번역하고, 파일이 바뀌면 갈아 끼워 줍니다.

**② 다 만든 뒤 — 하나로 묶어 주기 (빌드)**

만든 앱을 다른 사람에게 보여 주려면 인터넷 어딘가에 올려야 합니다.
그때 `npm run build` 를 하면 흩어져 있던 파일들을
**브라우저가 바로 읽을 수 있는 형태로 묶어 줍니다.**

비유하자면 ①은 **주방**, ②는 **포장**입니다.
요리하는 동안은 재료를 여기저기 펼쳐 놓고 쓰다가,
손님에게 낼 때는 한 접시에 담아 내보내는 것입니다.

비유는 여기까지입니다. 실제로 일어나는 일은 이렇습니다.

- ① 은 `localhost:5173` 이라는 주소를 열어 두고, 브라우저가 파일을 요청할 때마다
  그 파일을 번역해서 돌려줍니다. 파일이 바뀌면 브라우저에게 "그 파일 다시 받아 가" 라고 알려 줍니다.
- ② 는 `import` 로 이어진 파일들을 따라가면서 전부 모아, 결과를 `dist` 폴더에 만들어 줍니다.

09~13단원 내내 쓰는 것은 ① 입니다. ② 는 마지막에 한 번 해 봅니다.

## 대신 생기는 불편함 — 숨기지 않겠습니다

좋은 점만 적으면 나중에 배신감이 듭니다. 나빠지는 것도 같이 적습니다.

**① 더블클릭으로 안 열립니다**

`.jsx` 파일을 더블클릭하면 아무 일도 안 일어나거나 편집기가 열립니다.
**반드시 터미널에서 `npm run dev` 를 먼저 해야 합니다.**
이게 08단원에서 가장 많이 하는 실수입니다.

**② 터미널을 계속 켜 둬야 합니다**

`npm run dev` 를 한 터미널 창을 닫으면 서버가 꺼집니다. 화면도 안 뜹니다.
터미널은 켜 둔 채로 브라우저와 편집기를 오갑니다.

**③ `node_modules` 라는 큰 폴더가 생깁니다**

방금 실제로 만들어서 재 봤더니 이랬습니다.

| | |
|---|---|
| 폴더 개수 | 22개 |
| 파일 개수 | 437개 |
| 용량 | 약 62 MB |

React 하나만 쓰는 가장 작은 프로젝트인데도 이렇습니다.
**열어 볼 필요는 전혀 없습니다.** 이유는 개념02에서 설명합니다.

**④ 처음 한 번은 인터넷이 필요합니다**

`node_modules` 를 채우는 `npm install` 이 인터넷에서 받아 오기 때문입니다.
**다만 이 자료의 `실습프로젝트` 는 이미 받아 둔 상태입니다.**
그래서 여러분은 이 단계를 건너뜁니다.

## 안 바뀌는 것 — 이게 더 중요합니다

여기까지 읽고 "배운 걸 다시 배워야 하나" 걱정될 수 있습니다. 아닙니다.

**01~07단원에서 배운 React 문법은 전부 그대로입니다.**

JSX, 중괄호로 값 넣기, `className`, 컴포넌트, props, `children`,
`useState`, `onClick`, 조건부 렌더링, `map` 과 `key`, 폼 입력, 불변 갱신 —
**한 글자도 안 바뀝니다.**

07단원까지 만든 코드를 08단원으로 옮길 때 실제로 손대는 곳은 **세 군데뿐**입니다.

| | 01~07단원 (지금) | 08단원부터 |
|---|---|---|

## 정리

1. 08단원부터 `.html` 더블클릭 대신 터미널 `npm run dev` 로 진행합니다. React 문법이 바뀌는 것은 아닙니다.
2. **한계 1 — 파일을 못 나눈다.** 01~07단원 파일 49개가 27,880줄이고, 같은 `<style>` 85줄이 49번 복사돼 있습니다. Vite 는 `import`/`export` 로 파일을 나눠서 **고칠 곳을 한 곳으로** 만듭니다.
3. **한계 2 — 번역을 브라우저가 매번 한다.** `babel.min.js` 2,977 KB 를 F5 때마다 다시 켭니다. 콘솔의 노란 Babel 경고가 바로 "미리 번역해 두라" 는 뜻이었습니다. Vite 는 미리 번역해 둡니다.
4. **한계 3 — 라이브러리를 못 가져다 쓴다.** 파일을 직접 구해 순서까지 맞춰야 하고, 요즘 도구는 그런 파일을 잘 안 줍니다. **React 19 도 안 줍니다.** Vite 는 `npm install 이름` 한 줄이면 됩니다.
5. **한계 4 — 고칠 때마다 F5.** 게다가 F5 를 누르면 state 가 사라져 조작을 처음부터 다시 해야 했습니다. Vite 의 HMR 은 저장만 하면 **state 를 살린 채로** 바뀐 부분만 갈아 끼웁니다.
6. Vite 는 개발 중에는 작은 서버(`npm run dev`)이고, 다 만든 뒤에는 파일을 묶어 주는 도구(`npm run build`)입니다.
7. 대신 더블클릭으로는 못 열고, 터미널을 켜 둬야 하고, `node_modules`(약 62 MB)가 생깁니다. **`실습프로젝트` 는 준비가 끝나 있어서 여러분은 `npm run dev` 만 하면 됩니다.**
