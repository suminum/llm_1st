# 종합 실습 — 설비 점검 관리 시스템

01~10단원에서 배운 것을 **하나의 프로젝트**로 만듭니다.

이 폴더에는 완성본이 들어 있습니다.
여러분은 **빈 폴더에서 처음부터** 만드세요. 막히면 여기를 열어 보면 됩니다.

```bash
node server.js
# http://localhost:3000
```

---

## 무엇을 만드나

공장의 설비를 등록하고, 점검기록을 남기고, 사진을 붙이는 시스템입니다.

| 자원 | 설명 |
| --- | --- |
| 설비 | 이름 · 라인(A/B/C) · 상태(가동/정지/점검중) |
| 점검기록 | 어느 설비를 · 언제 · 누가 · 결과(정상/이상) · 내용 |
| 사진 | 설비마다 최대 3장 |

로그인은 05단원 방식(`Authorization: Bearer <키>`)을 씁니다.

| 증표 | 사람 | 역할 |
| --- | --- | --- |
| `key-user-1` | 김민준 | user |
| `key-admin-1` | 이서연 | admin |

## 지켜야 할 업무 규칙

이게 이 프로젝트의 핵심입니다. **전부 `services/` 에만** 있어야 합니다.

### 설비

1. 이름은 2~20글자, 라인은 A·B·C 중 하나
2. 같은 이름의 설비는 못 만든다 → `409 DUPLICATED`
3. 새 설비는 **언제나 `정지`** 로 시작한다 (본문의 `status` 는 무시)
4. `점검중` → `가동` 으로 **바로 못 간다**. 정지를 거쳐야 한다 → `409 CONFLICT`
5. `가동` 중인 설비는 **못 지운다** → `409 CONFLICT`

### 점검기록

6. 없는 설비의 기록을 물으면 `404`. **기록이 0건인 것과 다르다**
7. 없는 설비에는 기록을 남길 수 없다 → `404`
8. `result` 는 정상·이상, `내용` 은 필수(200자 이하)
9. **`result` 가 `이상` 이면 그 설비를 `점검중` 으로 바꾼다** ★
10. 담당자는 본문에서 안 받는다. **로그인한 사람**으로 정한다
11. 기록을 지워도 설비 상태는 안 되돌린다

### 사진

12. 설비당 최대 3장 → 넘으면 `409`
13. 확장자는 `.jpg .jpeg .png .gif` 만
14. 용량 제한을 둔다
15. **규칙에 걸리면 이미 저장된 파일을 지운다** ★ (고아 파일이 남으면 안 됨)
16. 지울 때는 **기록을 먼저, 파일을 나중에**

> ★ 표시한 9번과 15번이 이 실습에서 가장 중요합니다.
> 9번은 서비스 층이 왜 필요한지, 15번은 업로드가 왜 위험한지를 보여 줍니다.

## 주소

```
GET    /api/v1/equipments              목록 (page·limit·sort·q·line·status)
GET    /api/v1/equipments/:id          하나
POST   /api/v1/equipments              등록          admin
PATCH  /api/v1/equipments/:id          상태 변경      로그인
DELETE /api/v1/equipments/:id          삭제          admin

GET    /api/v1/equipments/:id/logs     그 설비의 점검기록
POST   /api/v1/equipments/:id/logs     기록 남기기    로그인
GET    /api/v1/logs                    전체 기록 (?equipmentId= 로 거르기)
GET    /api/v1/logs/:id                기록 하나
DELETE /api/v1/logs/:id                기록 삭제      admin

GET    /api/v1/equipments/:id/photos   그 설비의 사진
POST   /api/v1/equipments/:id/photos   사진 올리기    로그인 (필드 이름 photo)
GET    /api/v1/photos/:id/view         보기
GET    /api/v1/photos/:id/download     내려받기
DELETE /api/v1/photos/:id              사진 삭제      admin
GET    /api/v1/photos/orphans          고아 파일 확인 (시험용)

GET    /                               화면
```

응답 형식은 06단원 그대로입니다.

```json
{ "data": ... , "meta": { } }
{ "error": { "code": "...", "message": "...", "details": [ ] } }
```

## 폴더 구조

```
11_종합_실습/
  server.js          준비하고 listen 만
  app.js             조립 (미들웨어 → 라우트 → 정적 → 404 → 에러)
  routes/            주소 ↔ 함수, 누가 할 수 있는가
  controllers/       꺼내고 · 부르고 · 응답한다
  services/          업무 규칙 ★ 위 16가지가 전부 여기
  repositories/      읽고 쓴다
  middlewares/       인증 · 기록 · 업로드 · 에러처리
  utils/             AppError · 한국어(조사) · 파일이름
  public/            화면
  data/              JSON 파일 (자동 생성)
  uploads/           올린 사진 (자동 생성)
```

화살표는 한쪽으로만 갑니다.

```
routes → controllers → services → repositories
```

**아래층은 위층을 모릅니다.** 저장소가 서비스를 `require` 하면 안 됩니다.

## 만드는 순서 (권장)

한꺼번에 만들려 하지 마세요. **한 덩어리씩 만들고 그때마다 확인**하세요.

| 단계 | 만들 것 | 확인 |
| --- | --- | --- |
| 1 | `utils/` + `repositories/기본저장소.js` | `node` 로 저장소만 불러 시험 |
| 2 | `services/설비서비스.js` | 서버 없이 규칙 5개 확인 |
| 3 | `controllers/` + `routes/` + `app.js` + `server.js` | Postman 으로 설비 CRUD |
| 4 | `middlewares/인증.js` 붙이기 | 401·403 확인 |
| 5 | 점검기록 (규칙 6~11) | ★ 9번을 꼭 확인 |
| 6 | 사진 업로드 (규칙 12~16) | ★ 고아 0 확인 |
| 7 | `public/` 화면 | 브라우저로 |

2단계에서 이렇게 시험할 수 있어야 합니다. **서버를 안 켜고요.**

```js
const 서비스 = require("./services/설비서비스");

(async () => {
  try { await 서비스.삭제(1); }
  catch (e) { console.log(e.status, e.code); }   // 409 CONFLICT
})();
```

이게 안 되면 서비스에 `req`·`res` 가 섞여 들어간 것입니다.
