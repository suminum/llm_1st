개념 03 — 되돌리기와 .gitignore

00단원 · 개발환경과 Git

개념02의 깃연습 폴더에서 이어서 하세요.

이 단원에는 되돌릴 수 없는 명령이 하나 나옵니다 (섹션 4). 연습 폴더에서만 쓰세요.

섹션 1 — 아직 안 담았으면 restore

파일을 고쳤는데 마음에 안 듭니다. 아직 add 는 안 했습니다.

$ git status --short M index.html $ git restore index.html $ git status --short $ cat index.html <h1>안녕하세요</h1>

git status 가 아무것도 안 찍었습니다. 달라진 게 없다는 뜻입니다. 마지막 커밋 상태로 돌아갔습니다.

★ 고친 내용은 완전히 사라집니다

git restore 는 휴지통에 안 갑니다. Ctrl+Z 로도 못 되돌립니다. 아직 커밋 안 한 것이라 Git 도 모르는 내용이기 때문입니다.
지울 것이 확실할 때만 쓰세요.

✏️ 직접 해보기 1 — index.html 에 아무 줄이나 넣고 저장한 뒤 git restore index.html 로 되돌려 보세요. VS Code 에서 파일이 저절로 바뀌는 것을 보세요.

섹션 2 — 담은 것을 무르기

git add 를 했는데 "아, 이건 이번에 넣지 말걸" 싶을 때입니다.

$ git add . $ git status --short M index.html ← 담겼습니다 (첫째 칸이 M) $ git restore --staged index.html $ git status --short M index.html ← 담는 곳에서만 빠졌습니다 (둘째 칸이 M)

--staged 를 붙이면 담는 곳에서만 뺍니다. 고친 내용은 그대로 남아 있습니다. 기호가 M 에서 M 으로 옮겨 간 것을 보세요. (개념02 섹션4)

★ 완전히 없애고 싶으면 두 번 해야 합니다.
git restore --staged 파일 (담는 곳에서 빼고) → git restore 파일 (내용도 되돌리고)

✏️ 직접 해보기 2 — 파일을 고치고 add 한 뒤, --staged 있는 것과 없는 것을 차례로 써 보세요. git status --short 로 기호가 어떻게 움직이는지 보세요.

섹션 3 — 커밋한 뒤에는 revert

이미 커밋했습니다. 그런데 그 커밋이 잘못됐습니다. 기록은 남겨 두고, 내용만 되돌립니다.

$ git log --oneline 7411c6b 잘못된 줄을 넣었습니다 cca186a 설명 문단을 넣었습니다 9480c14 첫 페이지를 만들었습니다 $ git revert --no-edit HEAD [main 384ffb0] Revert "잘못된 줄을 넣었습니다" 1 file changed, 1 deletion(-) $ git log --oneline 384ffb0 Revert "잘못된 줄을 넣었습니다" 7411c6b 잘못된 줄을 넣었습니다 cca186a 설명 문단을 넣었습니다 9480c14 첫 페이지를 만들었습니다

기록이 줄지 않고 하나 늘었습니다. "그 커밋을 되돌렸다" 는 커밋이 새로 생긴 것입니다.
HEAD 는 "지금 있는 자리" 라는 뜻입니다. 제일 최근 커밋을 가리킵니다.
--no-edit 은 "메시지를 물어보지 마라" 입니다. 빼면 편집기가 열립니다.

★ 기록을 남기는 게 왜 좋으냐 — 남들과 같이 쓸 때 안전하기 때문입니다. 내가 기록을 지워 버리면 남의 컴퓨터에는 그 기록이 남아 있어서 서로 엉킵니다. revert 는 그런 일이 없습니다.

고친 것이 남아 있으면 못 합니다
$ git revert --no-edit HEAD error: your local changes would be overwritten by revert. hint: commit your changes or stash them to proceed. fatal: revert failed
"고친 것을 먼저 커밋하든지 치워 두라" 는 뜻입니다. 여기서도 hint: 가 답을 알려 줍니다.

✏️ 직접 해보기 3 — 아무 줄이나 넣고 커밋한 뒤 git revert --no-edit HEAD 로 되돌려 보세요. git log --oneline 이 어떻게 되는지 보세요.

섹션 4 — ★ reset --hard 는 지웁니다

인터넷에서 제일 많이 보이는 명령입니다. 그리고 제일 위험합니다.

$ git reset --hard HEAD~2 HEAD is now at cca186a 설명 문단을 넣었습니다 $ git log --oneline cca186a 설명 문단을 넣었습니다 9480c14 첫 페이지를 만들었습니다

커밋 두 개가 목록에서 사라졌습니다. HEAD~2 는 "지금 자리에서 두 칸 뒤" 라는 뜻입니다.

★★ 언제 쓰면 안 되나

이미 GitHub 에 올린 커밋에는 쓰지 마세요. 내 컴퓨터에서만 기록이 사라지고 GitHub 에는 남아 있어서, 다음에 올릴 때 거부당하거나 남의 작업을 지우게 됩니다.

올리기 전, 나 혼자 있는 커밋에만 쓰세요. 남들과 같이 쓰는 것은 revert 입니다. (섹션 3)

그래도 완전히 사라지지는 않습니다. git reflog 를 치면 최근에 있었던 자리들이 나옵니다. 거기 적힌 번호로 돌아갈 수 있습니다.
★ 다만 믿고 함부로 쓰라는 뜻이 아닙니다. 커밋 안 한 것은 reflog 에도 없습니다. 그건 진짜로 사라집니다.

✏️ 직접 해보기 4 — 연습 폴더에서 git reset --hard HEAD~1 을 해 보고, git reflog 로 사라진 커밋 번호를 찾아 보세요. (돌아가려면 git reset --hard 그번호)

섹션 5 — 기록하면 안 되는 것들

폴더 안의 모든 파일을 기록해야 하는 것은 아닙니다. 오히려 넣으면 안 되는 것이 있습니다.

node_modules/ 남이 만든 것을 받아 온 창고. 수만 개 파일입니다 .env 비밀번호·API 키가 든 파일 ★ dist/ build/ 빌드 결과. 소스에서 다시 만들 수 있습니다 .DS_Store 맥이 자동으로 만드는 것 Thumbs.db 윈도우가 자동으로 만드는 것

.gitignore 라는 파일을 만들고 여기에 적으면 Git 이 못 본 척합니다.

$ git status --short ?? .env ?? node_modules/ (.gitignore 파일을 만들고 두 줄을 씁니다) node_modules/ .env $ git status --short ?? .gitignore

.env 와 node_modules/ 가 사라졌습니다. 대신 .gitignore 자신이 나타났습니다.
★ .gitignore 는 같이 올려야 합니다. 팀원 모두가 같은 것을 무시해야 하니까요.

진짜로 무시되는지 확인하려면 —

$ git check-ignore -v .env .gitignore:2:.env .env
"몇 번째 줄의 어느 규칙에 걸렸는지" 를 알려 줍니다.

✏️ 직접 해보기 5 — 연습 폴더에 .env 파일을 만들고 git status --short 로 보이는 것을 확인한 뒤, .gitignore 에 적어서 사라지게 해 보세요.

섹션 6 — ★★ 이미 올린 파일은 .gitignore 가 안 먹습니다

이게 이 단원에서 제일 자주 사고가 나는 곳입니다. 실수로 .env 를 커밋한 뒤에 .gitignore 에 적었습니다.

여전히 따라다닙니다
(.gitignore 에 설정.txt 를 적었습니다) $ git status --short M 설정.txt ← ★ 그대로 보입니다 $ git check-ignore -v 설정.txt ← ★ 아무것도 안 나옵니다

.gitignore 는 "아직 모르는 파일" 에만 먹습니다. 이미 알고 있는(추적 중인) 파일은 계속 따라다닙니다.
★ check-ignore 가 아무 말도 안 하는 것이 신호입니다. 규칙이 틀린 게 아니라 이미 추적 중이라 검사 대상이 아닌 것입니다.
확인하려면 --no-index 를 붙입니다.

$ git check-ignore -v --no-index 설정.txt .gitignore:3:설정.txt 설정.txt
규칙은 멀쩡했습니다.

추적에서 빼면 됩니다
$ git rm --cached 설정.txt rm '설정.txt' $ git status --short D 설정.txt ← 저장소에서 지운다는 표시 (D = delete) $ git check-ignore -v 설정.txt .gitignore:3:설정.txt 설정.txt ← 이제 먹습니다
--cached 는 "저장소에서만 빼고 내 컴퓨터의 파일은 두라" 입니다.
★ --cached 를 빼면 진짜 파일이 지워집니다. 조심하세요.
★★★ 그런데 비밀번호가 샌 것은 이걸로 안 끝납니다

git rm --cached 를 하고 커밋해도 옛 기록에는 남아 있습니다. 누구든 옛 커밋을 꺼내 보면 그 비밀번호가 보입니다.

키나 비밀번호가 한 번 올라갔으면, 그 키를 폐기하는 것 말고 방법이 없습니다. 지우는 것으로는 해결되지 않습니다.
★ 그래서 .gitignore 를 처음에 만드는 것이 중요합니다.

✏️ 직접 해보기 6 — 아무 파일이나 커밋한 뒤 .gitignore 에 적어 보세요. git status 에 계속 보이는 것을 확인하고, git rm --cached 로 빼 보세요.

섹션 7 — 자주 하는 실수

[실수 1] restore 로 지운 것을 되찾으려 함

못 찾습니다. 커밋 안 한 것은 Git 도 모릅니다. (섹션 1)

[실수 2] 올린 커밋에 reset --hard

남들과 엉킵니다. 올린 뒤에는 revert 를 쓰세요. (섹션 3·4)

[실수 3] .gitignore 를 나중에 만듦

섹션 6 그대로입니다. 프로젝트를 만들자마자 만드세요. 첫 커밋 전에 만드는 것이 제일 좋습니다.

[실수 4] git rm 에 --cached 를 빼먹음

진짜 파일이 지워집니다. 항상 --cached 를 붙였는지 보세요.

[실수 5] .gitignore 에 적었는데 안 먹는다고 규칙을 계속 고침

규칙이 아니라 이미 추적 중이라서입니다. git check-ignore -v --no-index 로 규칙이 맞는지부터 확인하세요. (섹션 6)

[실수 6] node_modules 를 통째로 올림

파일이 수만 개라 올리는 데 한참 걸리고, 받는 사람도 괴롭습니다. package.json 만 있으면 npm install 로 다시 만들어집니다.

정리

  • 안 담았으면 git restore 파일. 되찾을 수 없으니 조심.
  • 담았으면 git restore --staged 파일. 내용은 그대로 남습니다.
  • 커밋했으면 git revert HEAD. 기록을 남기며 되돌립니다.
  • ★ git reset --hard 는 기록을 지웁니다. 올리기 전, 나 혼자일 때만.
  • .gitignore 는 프로젝트를 만들자마자 만듭니다.
  • ★★ 이미 추적 중인 파일에는 .gitignore 가 안 먹습니다. git rm --cached 로 빼야 합니다.
  • ★★★ 비밀번호가 한 번 올라갔으면 지워도 기록에 남습니다. 키를 폐기하세요.
